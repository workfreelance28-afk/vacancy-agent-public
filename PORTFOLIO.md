# Vacancy Agent — portfolio case

## Что делает

Vacancy Agent помогает находить Junior/Junior+ вакансии для первого коммерческого опыта в AI-интеграции.

Базовый сценарий (MVP): система получает вакансии из внешних источников, применяет жёсткие фильтры, оценивает оставшиеся вакансии локальной LLM через LM Studio, сохраняет результат и отправляет подходящие карточки в Telegram. Отклик остаётся под контролем человека: пользователь сам выбирает вакансию, проверяет её, отправляет резюме и пишет сопроводительное письмо.

На втором этапе (Stage 2) этот рабочий MVP превращён в небольшой измеряемый production-like сервис: FastAPI + PostgreSQL, очередь фоновых задач с retry, Docker Compose и CI, versioned evals с regression gate, структурированная наблюдаемость и безопасный MCP-инструмент с human-in-the-loop подтверждением.

## Моя роль

Я спроектировал продуктовый сценарий, архитектуру пайплайна и границы ответственности между Python-кодом, внешними источниками, локальной LLM, БД, Telegram, MCP-клиентом и пользователем — и довёл его до воспроизводимого, тестируемого production-like состояния.

Моя зона ответственности:

- продуктовая логика поиска и отбора вакансий, критерии жёсткой фильтрации;
- интеграция источников вакансий и подключение локальной модели через LM Studio;
- API-контракты, PostgreSQL-адаптер и миграции;
- очередь фоновых задач: retry, timeout, идемпотентность, диагностируемый сбой;
- Docker Compose и CI (lint, тесты, secret scan, eval regression gate);
- versioned golden dataset и regression gate по качеству/latency/cost;
- структурированные JSON-логи, request/job correlation ID, безопасные метрики;
- безопасный MCP tool с backend-валидацией и human-in-the-loop approval;
- тесты, обработка ошибок и явные ограничения на каждом слое.

## Архитектура

Основной путь:

```text
SuperJob / Habr / HH
→ нормализация вакансий
→ жёсткие фильтры
→ локальная LLM-оценка через LM Studio
→ хранилище (SQLite/PostgreSQL)
→ Telegram
→ ручное решение пользователя
```

Добавлено на Stage 2:

```text
FastAPI API (health/ready, jobs, вакансии)
→ очередь фоновых задач → worker (retry, timeout, идемпотентность)
→ structured JSON-логи + метрики (request/job correlation ID)
→ MCP tool: schema → preflight → human approval (elicitation) → повторная
  backend-валидация → генерация черновика
```

Ключевой принцип не изменился: LLM предлагает оценку и черновик, но не принимает критические решения за пользователя и не отправляет отклики автоматически. Ни модель, ни аргументы tool-вызова не могут сами себя авторизовать — подтверждение всегда приходит через отдельный канал, которым управляет человек.

## Что доказывает проект

Проект показывает, что я умею не только собрать AI workflow вокруг реальной пользовательской задачи, но и довести его до состояния, близкого к продакшену:

- отделять детерминированную бизнес-логику от LLM-этапа;
- проектировать human-in-the-loop сценарий — на уровне продукта и на уровне протокола (MCP elicitation);
- строить API-контракты, миграции и очередь с гарантией отсутствия дублей при повторной доставке;
- организовывать воспроизводимый локальный запуск (Docker Compose) и CI-пайплайн проверок;
- строить versioned evaluation с честным regression gate по качеству, latency и стоимости;
- делать минимальную, но полезную наблюдаемость: диагностировать инцидент по логам/метрикам без доступа к БД и без раскрытия секретов;
- безопасно подключать LLM tool calling: backend, а не модель, решает, что допустимо, и человек, а не аргумент функции, подтверждает критическое действие;
- честно документировать ограничения вместо того, чтобы их скрывать.

## Тесты

Проект покрыт автоматическими тестами на всех слоях:

- unit-тесты доменной логики, фильтров, настроек, PostgreSQL/SQLite-адаптеров, очереди и worker;
- integration-тесты API, очереди и MCP-протокола против настоящей БД;
- тесты наблюдаемости: один сквозной incident (transient failure → retry → final failure), диагностируемый только по JSON-логам и метрикам;
- тесты безопасности MCP tool: попытка модели подделать approval полем в аргументах, отказ/отмена человека, отсутствие поддержки approval у клиента — везде fail-closed;
- offline evaluation regression gate на versioned golden dataset (50 кейсов).


(32 skip — тесты, требующие подключения к живой тестовой PostgreSQL, не поднятой в этом окружении; в CI они зелёные.)

## Ограничения

- Это личный рабочий инструмент, а не коммерческий SaaS.
- Источники вакансий могут менять API, HTML и правила доступа.
- HH оставлен как резервный источник из-за ограничений анонимного поиска.
- Habr Career используется через ограниченный HTML-parser публичного каталога, не через официальный API.
- Локальная LLM может ошибаться, поэтому её оценка не является финальным решением.
- Генерация резюме, писем и автоматическая отправка откликов не входят в текущий production-путь; MCP tool готовит только локальный черновик и никуда его не отправляет.
- MCP-сервер работает только локально (stdio) — без remote MCP и публичного endpoint.
- Платные API не подключаются без отдельного объяснения цены, назначения и рисков.

## Что не публикуем

В публичную витрину нельзя переносить:

- `.env`, любые реальные токены/API-ключи и строки подключения к БД (DSN);
- локальную базу данных и её содержимое;
- персональные данные, контакты и приватные версии резюме;
- реальные чаты Telegram и chat_id;
- сырые ответы LLM и raw prompt/reasoning, если они содержат приватный контекст;
- локальные артефакты из `output/` и `data/`;
- `.venv`, cache-папки, `__pycache__` и `.pyc`;
- внутреннюю историю ревью/итераций, если она раздувает кейс и не помогает работодателю понять результат.
