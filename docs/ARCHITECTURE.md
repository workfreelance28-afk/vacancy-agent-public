# Архитектура

## Контур системы

```text
Планировщик
    ↓
SuperJob API → сборщик → нормализация → жёсткие фильтры → хранилище
                                                         ↓
                                                   Qwen / LM Studio
                                                         ↓
                                                проверка FIT SCORE
                                                         ↓
                                                     Telegram
                                                         ↓
                                            «Подготовить отклик»
                                                         ↓
                                           Qwen / LM Studio (локально)
                                                         ↓
                                          анализ + резюме + письмо
```

В MVP 1 ветки Qwen и Claude отсутствовали — после фильтрации вакансия сразу формировалась для Telegram. **С TASK-007 (`docs/DECISIONS.md`, ADR-021, коммит `b6c884f`) Qwen подключён к `application/daily_scan.py`**: между жёсткими фильтрами и Telegram сценарий вызывает `LMStudioQwenClient.assess`, и только вакансии, прошедшие порог (`passes_relevance_threshold`), уходят в Telegram. Оценка (score/relevant/recommendation/strengths/gaps/risks) и модель сохраняются вместе с вакансией (ADR-022). **TASK-011 (`docs/DECISIONS.md`, ADR-034–ADR-037) реализована и принята независимым ревью Codex**: тот же локальный Qwen подключён как отдельный use case со своим prompt/schema/generator (`integrations/application_draft_client.py`, `application/application_drafts.py`), не расширяя `QwenClient.assess`. По явному `POST /api/v1/vacancies/{id}/application-drafts` для одной уже отфильтрованной и оценённой вакансии Qwen готовит проверяемый черновик отклика (`ApplicationDraft`) с evidence-ссылками на versioned Master Profile; черновик сохраняется в SQLite (`application_drafts`) и читается через `GET .../application-draft`. Платная Claude-ветка не выбрана (ADR-034).

**Источник вакансий сменился с HH.ru на SuperJob** (см. `docs/DECISIONS.md`, ADR-013/ADR-014): HH с апреля 2026 закрыл анонимный доступ к поиску вакансий, и на этом источнике проект был построен изначально (ADR-006/ADR-007). Источник — переключаемый компонент (`domain/ports.VacancySource`, реализации `HttpxHHClient`/`SuperJobClient`, выбор через `Settings.vacancy_source`), а не жёстко зашитый выбор — HH-реализация не удалена, только отключена по умолчанию.

## Ответственность компонентов

| Компонент | Ответственность | Не отвечает за |
|---|---|---|
| Клиент источника вакансий (`SuperJobClient`, переключаемый `HttpxHHClient`) | запросы, пагинация, лимиты, повторные попытки | оценку вакансий |
| Нормализатор | перевод ответа источника во внутреннюю модель | бизнес-решение |
| Python-фильтр | детерминированные критерии | смысловой LLM-анализ |
| Репозиторий данных | вакансии, статусы, идемпотентность | пользовательский интерфейс |
| Qwen-клиент | локальная массовая оценка | финальный отклик |
| Telegram-бот | показ карточек и приём команд | поиск вакансий |
| Будущий backend глубокого анализа | анализ по явному запросу | массовую фильтрацию |
| Планировщик | запуск сценария | бизнес-логику сценария |

## Предлагаемые слои кода

```text
src/
  domain/          # сущности, статусы, правила
  application/     # сценарии использования
  integrations/    # SuperJob, HH (переключаемый), Telegram, LM Studio, Claude
  persistence/     # база данных и репозитории
  config/          # типизированная конфигурация
tests/
  unit/
  integration/
```

Структура является предложением для реализации MVP 1 и должна быть подтверждена первой технической задачей.

## Поток обработки вакансии

1. Получить страницу результатов источника вакансий (SuperJob; HH — переключаемый).
2. Нормализовать данные и сохранить исходный `hh_id` (поле сохранило имя из TASK-002 — это внешний идентификатор вакансии независимо от источника, не переименовано, чтобы не трогать схему хранилища ради косметики).
3. Проверить, обрабатывалась ли вакансия ранее.
4. Применить жёсткие фильтры с фиксированной причиной отказа; если отклонена — сохранить с причинами, дальше не идёт.
5. Если принята — запросить оценку Qwen и провалидировать JSON (ADR-021). Техническая ошибка — не сохранять, повторить на следующем прогоне (fail-closed/retryable, ADR-020/022).
6. Если итоговый балл не ниже порога (`passes_relevance_threshold`) — отправить карточку в Telegram и сохранить вместе с оценкой; если ниже — сохранить с оценкой, но не отправлять (ADR-022).
7. Обработать действие пользователя и изменить статус атомарно.
8. По TASK-011 явный синхронный POST для одной прошедшей вакансии
   вызывает локальный Qwen. Python проверяет schema/evidence, SQLite хранит
   один draft на vacancy; status не меняется (ADR-034/ADR-035).

## Надёжность и безопасность

- Все внешние вызовы имеют тайм-ауты и ограниченные повторы.
- Повторы используют задержку и не обходят лимиты API.
- Уникальный индекс по `hh_id` защищает от дубликатов.
- Каждая причина фильтрации сохраняется для отладки.
- Невалидный ответ LLM не считается успешным анализом.
- Telegram callback проверяется по допустимым действиям и вакансии.
- Логи не содержат API-ключи, полное резюме и секреты.
- Автоматический отклик без подтверждения пользователя запрещён.

## Конфигурация

Ожидаемые группы настроек:

- источник вакансий: `VACANCY_SOURCE` (`superjob`/`hh`);
- SuperJob: ключ (`X-Api-App-Id`), ключевые слова поиска, город, параметры пагинации;
- HH (переключаемый): поисковые запросы, регион, период, параметры пагинации;
- фильтры: зарплата, формат, опыт, include/exclude слова;
- Telegram: токен, разрешённые chat ID;
- Qwen: URL LM Studio, имя модели, порог, тайм-аут;
- Claude: модель, лимиты, тайм-аут;
- расписание и часовой пояс;
- строка подключения к базе.

Точные имена переменных окружения фиксируются в ходе TASK-001 и отражаются в `.env.example` без секретных значений.
